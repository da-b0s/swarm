**SafeERC20 changes and why they matter:**

`DealFactory` and `Settler` both `using SafeERC20 for IERC20`. The three goods-token call sites are now:
- Stock deposit in `DealFactory.postDeal`: `token.safeTransferFrom(...)` — the `bool ok` check and `TransferFailed` guard are removed; SafeERC20 handles both the no-return-value case (USDT-style) and explicit `false` returns. The balance-delta check stays because it catches fee-on-transfer tokens, which is a distinct problem from missing return values.
- `DealFactory.pullGoodsForSettler`: `IERC20(deal.goodsToken).safeTransfer(settler, amount)` — same reasoning.
- `Settler.claimGoods`: `IERC20(token).safeTransfer(msg.sender, amount)` — the misleading `if (!ok) revert NothingToClaim()` branch is gone. With `safeTransfer`, the token's own revert propagates directly to the caller.

**Test fixes:**

`test_Post_MaxBuyersOutOfRange_Zero`: the `_params` helper guarded `maxBuyers == 0 ? 10 : maxBuyers` specifically to avoid accidents, which defeated this test. Replaced with a literal `PostParams` struct.

`test_Post_MinUnitsZero`: `stdTiers[0].minUnits = 1 > p.minUnits = 0` triggers `TierMinUnitsExceedsMin` before `MinUnitsZero`. Fixed with a single tier having `minUnits = 0`, which passes the tier-check (0 ≤ 0) and lets the `MinUnitsZero` check fire.

`test_Claims_ReentrantGoods`: the reentrant mock called back into `settler.claimGoods` during `factory.pullGoodsForSettler` inside `settle`, which holds the Settler's reentrancy lock. The fix: arm the mock (`setSettler`) only after `_settle` completes, so reentrancy is attempted only during the buyer's `claimGoods` call.

`test_Strand_SingleBuyerCanAlwaysWithdraw`: B1 commits 15 units at $0.75/unit = 11,250,000 USDC. The test had only funded 10,000,000, causing an arithmetic underflow in the mock's balance arithmetic. Fixed by funding 15,000,000.
